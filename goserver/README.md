# schedsim-go — the scheduler as a library, not a binary

An exploratory alternative backend for schedsim. The rest of this repo
answers "where would the real scheduler place this?" by running the
**unmodified kube-scheduler binary** against a **fake HTTP apiserver**
(`image/server/`). This does the same job a different way: it imports
`k8s.io/kubernetes/pkg/scheduler` as a Go library and calls it directly,
in-process, against a fake `client-go` clientset instead of a fake
apiserver. Same public API (`GET /healthz`, `POST /run`, identical
request/response shapes) — the `schedsim` CLI can't tell the two apart —
different internals.

## Why this is worth looking at

The Python backend's fake apiserver (`store.py` + `fakeapi.py`, ~640
lines) exists only because an external binary needs *something* speaking
real Kubernetes REST/watch semantics to talk to. Cut the binary out of the
picture and that whole HTTP layer goes with it: the scheduler and its
client just need an object store behind the same `clientset.Interface` it
already codes against, and `k8s.io/client-go/kubernetes/fake` already
*is* one — it's what upstream's own scheduler unit tests use. What's left
to write is genuinely small; see [The seam](#the-seam-what-this-repo-actually-owns) below.

## Trade-offs against the binary+fake-apiserver approach

**In this alternative's favor:**
- No separate OS process, no real network hop, no protobuf-vs-JSON or
  client-side QPS-limiting gotchas to work around (see the top-level
  README's "How it works" section) — those all existed to make an
  external binary treat the fake apiserver as trustworthy, and don't
  apply to a function call.
- Faster to start and to run: no binary download, no HTTP round trips
  between scheduler and store.
- Even less custom surface than the Python backend: no request routing,
  no query-param/watch/discovery emulation, no strategic-merge-patch
  implementation — `client-go`'s fake clientset already provides all of
  that generically.

**Against it:**
- `k8s.io/kubernetes` is explicitly not meant to be imported as a library
  by anyone outside `kubernetes/kubernetes` itself — there's no semver
  contract on `pkg/scheduler`'s Go API, and internal packages can and do
  move or change shape between patch releases. `go.mod`'s replace block
  (needed because the module's own internal `replace ... => ./staging/...`
  directives aren't transitive) has to be regenerated by hand from
  upstream's `go.mod` on every version bump, not just the one version
  string `image/Dockerfile` pins today.
- This never runs the artifact that actually ships to production — a
  real cluster runs the kube-scheduler *binary*. A behavior change that
  only shows up in `cmd/kube-scheduler`'s own wiring (flag defaults,
  admission-adjacent startup code) wouldn't show up here. The
  binary+fake-apiserver approach is closer to "what would really happen."
- Pulls in kube-scheduler's full dependency graph as Go modules (~500MB
  in the module cache) rather than downloading one pinned binary.

## The seam: what this repo actually owns

Everything that decides *where a pod goes* — filtering, scoring,
preemption, the default profile, even patching the real
`PodScheduled=False` condition with the real `FitError` message on
failure — is `k8s.io/kubernetes/pkg/scheduler`, unmodified, called the
same way upstream's own tests call it
(`pkg/scheduler/scheduler_test.go`'s `setupTestScheduler` is the pattern
`internal/simcluster/cluster.go` follows). This package supplies just
enough around that to make it runnable standalone:

- `internal/simcluster/cluster.go` — builds a fake `clientset.Interface`,
  hands it to `scheduler.New()` with no options (which is what pulls in
  the real default profile), and starts the informers and `sched.Run()`.
  The one thing the fake clientset doesn't do that a real apiserver would
  is understand the `pods/binding` subresource the scheduler's bind step
  posts to — so there's a ~15-line reactor translating that into a plain
  `pod.Spec.NodeName` write, directly analogous to `store.py`'s
  `bind_pod`. A second small reactor assigns UIDs on create, since the
  fake clientset never does and the scheduler keys its queues by UID.
- `internal/simcluster/manifests.go` — turns the same simplified
  `nodes:`/`workloads:` shape (and raw `kind: Node`/`kind: Pod`
  passthrough) the top-level README documents into real `corev1.Node`/
  `corev1.Pod` values, mirroring `simulate.py`'s `node_manifest`/
  `pod_manifests`.
- `internal/simcluster/run.go` — apply nodes, apply pods, poll until
  every pod is bound or durably unschedulable, clean up; a direct port of
  `simulate.py`'s `run()`/`_wait_for_scheduling()`, down to the
  no-progress timeout semantics.
- `main.go` — the same two-endpoint HTTP surface as `image/server/app.py`.

Keeping that list short is the whole point: it's what stays cheap to
carry forward across kube-scheduler versions. The expected update path
is the same as today's — bump a pinned version (`k8s.io/kubernetes
v1.31.4` in `go.mod` here, `K8S_VERSION` in `image/Dockerfile` there) —
plus, unlike the binary, regenerating the `replace` block from upstream's
`go.mod` (see the comment at the top of `go.mod`).

## Known behavioral differences from the Python backend

- No real HTTP apiserver surface: `kubectl exec`-style poking
  (`podman exec schedsim kubectl get pods`) and direct API access
  (`http://127.0.0.1:8080/api/v1/...`) don't exist here — `/healthz` and
  `/run` are the entire API.
- The fake nodes aren't tainted (`schedsim.local/fake-node`) the way the
  Python backend's are. That taint exists there so nothing *else*
  scheduling against a shared fake apiserver could land a pod on a fake
  node by accident; there is no "else" here — this process's fake
  clientset only ever exists for one run.
- Node objects are still stamped `Ready=True` for informational parity,
  though no in-tree default plugin actually gates on it (only
  `.spec.unschedulable` and taints do).

## Running it

```bash
cd goserver
go run .                       # listens on :8080 (or $PORT)
curl http://127.0.0.1:8080/healthz
```

Or as a container, exactly like the top-level `run.sh` flow:

```bash
podman build -t schedsim-go-image goserver
podman run -d --name schedsim-go -p 8081:8080 schedsim-go-image
```

Point any existing scenario file at it with the same request shape
`apiclient.py` sends — this is the whole point, the two backends are
interchangeable at the API boundary:

```bash
python3 -c "
import json, yaml
cfg = yaml.safe_load(open('../examples/demo.yaml'))
print(json.dumps({'nodes': cfg['nodes'], 'workloads': cfg['workloads'],
                   'timeout': 15, 'keep': False, 'progress': True}))
" | curl -sS -X POST http://127.0.0.1:8081/run \
       -H 'Content-Type: application/json' --data @-
```

The `schedsim` CLI itself isn't wired up to point at this backend (it
manages the Python image's container lifecycle by name via
`schedsim/cluster.py`); pointing it here instead would mean adding a
`--server` override there, which felt like a separate change from this
exploration.
